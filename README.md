# 稳定币版 "Alipay+"：让日本钱包扫东南亚国家二维码

INSPAY 技术方案预研。问题：**如何让 PayPay 这样的日本钱包，在东南亚各国直接扫当地国家统一二维码（Thai QR / QRIS / DuitNow / SGQR / VietQR / QR Ph / KHQR / LAO QR）付款，并用稳定币替代传统跨境清结算？**

## 一页结论

1. **前台像 Alipay+**：钱包只对接一套 API（识别 → 报价 → 支付 → 通知 → 退款 → 结算单）；网络负责解析 EMVCo 国家码、识别方案、查询商户名、路由到当地伙伴、锁汇、风控。
2. **商户侧直接用国家码 + 国家快速支付系统**：由各国持牌参与者（银行/持牌钱包，或交换机跨境网关）把本币实时贷记到商户原有账户，商户零改造、照常收本币、用自己的银行 App 看到账。
3. **稳定币只在机构之间，价值因国而异**：用户付日元、商户收本币；PayPay → 网络仍是日元银行电汇。网络在新加坡枢纽持有 USDC 金库，按周期净额结算：
   * **新加坡、菲律宾**的伙伴直接链上收 USDC，可 7×24、日内多次结算；垫付风险由链上保证金合约兜底（合约未审计，审计前只用于这两国）；
   * **泰国、马来西亚、印尼、越南、柬埔寨、老挝**（含 Phase 1 首选的泰国）稳定币不入境：枢纽出金后以工作日 USD 电汇付款，由境内持牌银行换汇（T+0–T+1 工作日）。伙伴侧的到账速度、节假日停摆和代理行环节与传统电汇相同；稳定币只带来枢纽侧多国共享流动性和链上批次存证，还多出 JPY→USDC→USD 两次兑换（10 章假设约 15 bps）。这些国家以"工作日日结 + 法币电汇"为基线，垫付风险用结算行的银行保函/SBLC 覆盖（泰国另可用 NRQC 泰铢预存池）；是否经 USDC 中转，由 10 章 10.6 法币基准对照的实测报价决定；
   * 香港是第二枢纽候选，不是目的国。

   这样不触碰多数东南亚国家"加密资产不得作为支付手段"的规定。Alipay+ 已有稳定币清算个案（新加坡 StraitsX × Grab，XSGD），"机构间稳定币结算"本身不是差异化；差异化在于日本钱包可扫泰、越、印尼国家码（印尼的 METI–BI 框架通道 Netstars / JPQR Global 尚无日本钱包接入，见 01 章 1.1）+ 锁定报价（电汇国家以境内结算行书面承诺锁价为前提）+ 链上结算国家的日内结算。
4. **四条接入路径**（[01 章 1.5](docs/01-architecture.md#15-接入各国国家码的四种路径)）：
   * **A** 交换机跨境网关：覆盖该国参与跨境受理银行发出的全部商户码，商务周期长；
   * **B** 本地银行合作：**B1 收单行 on-us** 只覆盖该行商户码，落地快；**B2 发卡侧赞助行**由一家快速支付系统直连成员代境外钱包发起贷记，技术上可覆盖全国国家码商户（先例 GLN × SCB，2023-12，SCB 称覆盖全国 Thai QR 商户，现状未核实），但须央行/交换机确认"境外发起"的口径与外汇定性；
   * **C** 借道 Alipay+ / HIVEX（最快但不可控）；印尼、柬埔寨可利用 METI 框架下的 Netstars / JPQR Global 交换——它不是钱包，出境方向缺日本钱包一端，由本网络作为日方发行侧聚合者把 PayPay 接入；
   * **D** Nexus（目标 2027）：首版只做账户到账户，日本不是成员，日本加入前不是日本钱包的扫码通道。
5. **日本侧与枢纽牌照**：PayPay 作为為替取引主体（与其韩国/台湾海外支付同构），网络主体放在离岸，JPY→USDC 在境外兑换，网络的日本实体不经手日元——需日本律师确认。新加坡枢纽的客户全在境外，不持 PS Act 牌照即落入 DTSP 制度（2025-06-30 生效、无过渡期）：要么申请 MPI 牌照（跨境汇款 + DPT 服务），要么由持牌的 StraitsX、dtcpay 做稳定币兑换与托管、网络只做规则与技术——新加坡法律意见是 Phase 0 阻断项。PayPay 把付款人信息传给境外网络与 LSP，属个人信息保护法第 28 条"向外国第三方提供"（06 章 6.7，需律师确认）。
6. **竞争与经济账**：Alipay+、HIVEX（二者都借助 PayPay 的商户网络与 PayPay 海外模式）之外，已能扫 VietQR / QR Ph 的加密钱包（Bitget、RedotPay）是替代通道，PayPay × Visa 也可能成为另一条出境路线（具体条款未查到）；Netstars / JPQR Global 截至 2026-10 没有日本钱包接入、入境只覆盖少数张贴其码的商户，目前不是有效替代（见 01 章 1.1）。窗口有限（判断）。网络汇差与网络费加在用户价格上，PayPay 的 3.85% 不变；Alipay+ 下由收单侧向钱包付 wallet interchange，所以 BD 须给出对标 Alipay+ 的钱包分润方案（10 章 10.7）。

## 第一步

Phase 1 选**泰国**（理由见 [05 章 5.1](docs/05-country-playbooks.md)、[08 章 Phase 1](docs/08-roadmap.md)）：
* 与 SCB 谈 B2 发卡侧赞助模式（GLN 先例），或与 Krungsri（MUFG 系，已有日本合作）谈 B1/B2；
* 结算按泰国工作日日结、USD 电汇，截止时间与节假日日历对齐结算行，不做小时结；
* 并行做 08 章"最便宜的下一步验证"：PayPay 技术对齐、目标银行确认、日本与新加坡法律意见、实盘报价测算。

## 代码

* [`reference-impl/`](reference-impl/)：零依赖 TypeScript 参考实现（EMVCo 解析、各国 profile、报价、支付编排、复式账本、稳定币净额结算、HTTP API），需 Node ≥ 22.18。`cd reference-impl && npm test` / `npm run demo`；`npm run serve` 启动 HTTP API（只监听 127.0.0.1，默认端口 8787）：设置 `MPP_SECRET`、`LSP_SECRET`、`OPS_SECRET` 后要求 HMAC 签名请求（`client-id` / `signature` 头，角色 mpp / lsp / ops），都不设时是无鉴权的本地演示模式，不得对外暴露。参考实现的报文格式与 07 章规范不同，差异见 07 章 7.6，对外联调以 07 章为准；
* [`contracts/`](contracts/)：链上结算保证金合约草图（Solidity，未审计）与 in-process EVM 测试，运行 `cd contracts && npm install && npm test`（需联网安装 ethers / ganache / solc）。生产前仍缺暂停/守护多签、伙伴停用与审计；
* [`docs/research/`](docs/research/)：调研原始输出（事实清单与报告），其中有被核实轮推翻的条目，结论以正文为准。
